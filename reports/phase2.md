# tidal 第二阶段报告（自监督投影、校准与弃权、身份无关、场景通用、全双工控制、影子并行）

> 日期：2026-10-08（UTC+8）｜全程只用 CPU（8 核 Xeon；训练单线程 nice 19，评测 1–2 线程）
> 原则不变：评测只用真实留出数据（第一阶段的同一套行、同一套 会话×小时 分块 bootstrap）；合成数据只用于训练，或在报告中明确标为"合成"；真实聊天不进 git、不发给任何外部 API。本阶段**没有调用任何 LLM API**（新增的直播 / 1:1 流是脚本生成的）。
> **公开版说明**：本报告不含任何真实消息、会话标识或部署细节；真实数据、在真实数据上训练的权重、逐事件输出都不公开。

## 0. 结论速览

1. **VAP 式未来事件投影已实现**（只用时间和相对角色，覆盖全部事件，包括 71% 没有文本的消息）。它作为自监督目标有一点用，但**没有超过同特征上的简单逻辑回归**：真实测试集上 20 个投影输出的平均 ROC-AUC，模型 0.675 vs LR 0.668（时间切分，Δ +0.008 [−0.020, +0.036]），未见群上 0.659 vs 0.671（Δ −0.015 [−0.051, +0.017]）。预训练相对不预训练 +0.025 [−0.006, +0.061]，不显著。
2. **零样本读出**（只做投影预训练、不看任何下游标签）在"自我续话"上显著超过 val 选出的最强基线（PR-AUC 0.728 vs 0.700，Δ +0.031 [+0.015, +0.057]），但不超过 test 上事后最好的 GBDT（0.762）。
3. **下游各头**：第二阶段选定模型 `P2a_s1`（VAP 预训练 → 多任务微调，0.50M 参数）和第一阶段模型 `T_rs_gru_s1` **基本持平**，所有"第二阶段 − 第一阶段"的 Δ 都不显著（被叫头在未见群上 +0.116 [+0.000, +0.272]，只有 8 个正例，不可信）。和强基线相比仍然**没有稳定显著的提升**；人类接话（时间切分）显著更差（−0.034 [−0.067, −0.007]），未见群上的"说/等/不说"仍显著更差（−0.097 [−0.168, −0.027]，和第一阶段一样）。
4. **校准**：温度缩放后 ECE 只有 EOT 显著下降（时间切分 0.060 → 0.036，Δ −0.024 [−0.043, −0.006]）；自我续话反而变差（0.094 → 0.142，CI 跨 0），原因是 val 和 test 的正例率不同（0.42 vs 0.64）。**弃权**：风险-覆盖曲线（AURC）相对第一阶段没有显著差别；相对最强基线只有重检延迟（未见群）显著更好（−0.060 [−0.089, −0.030]），第一阶段模型同样做得到。
5. **身份无关 + 冷启动**：模型只用相对角色，新会话不需要注册任何人。在未见群上从零历史"加入"，EOT / 人类接话在前 20 条内就接近有完整历史时的水平；自我续话前 50 条低约 0.1 PR-AUC（CI 跨 0），重检延迟前 50 条显著更低（macro-F1 −0.03 到 −0.06）。**按会话在线自适应**只带来很小的收益（续话前 100 条 log-loss −0.080 [−0.156, −0.003]，重检前 20 条 macro-F1 +0.030 [+0.003, +0.056]），对被叫头有害。
6. **场景通用**：输入里没有场景枚举，参与人数是连续特征（未知时置零）。留一场景评测显示**跨场景几乎不迁移**：没见过直播的模型在合成直播上 EOT / 续话的 PR-AUC 只等于正例率（没有区分力）；"回应哪条弹幕"的 hit@1 是 0.066，低于"回应最新一条"启发式（0.105）。完全不用群聊数据训练（只用合成直播 + 1:1）的模型，在真实群聊上 EOT 只等于先验、续话低于先验。详见 §4。**直播和 1:1 流都是脚本合成的**，这部分只能说明管线可用，不能说明真实效果。
7. **全双工 tick 控制器（100 ms）**：多路输入（事件、音频帧、视觉帧、她自己的输出状态）、控制和内容分离。单线程 CPU 上每 tick p50 0.64 ms / p95 0.82 ms（每 tick 1 个事件），每 tick 20 个事件（每秒 200 条，直播高峰）时 p50 24.5 / p95 38.7 ms；**10 Hz 下 RTF ≤ 0.39，满足 5–10 Hz 要求**。满载可持续的频率：空闲约 6,800 Hz，每 tick 1 个事件约 1,500 Hz，每 tick 20 个事件约 41 Hz。合成 sanity 测试里，调过参的规则控制器在"让出"（0.882 vs 0.807 F1）和"冷场时主动开口"（0.972 vs 0.817）上**比模型更好**；模型在"开始 / 被打断后继续 / 附和"上更好。音频和视觉只是接口，没有真实前端。
8. **ONNX**：`P2a_s1` 导出 2.0 MB，1,000 个真实窗口上和 PyTorch 的最大差 2.7e-7，决策 100% 一致。
9. **影子模式**：新模型已作为第二个系统接入原有的定时任务，和第一阶段模型在**同一批延迟标签**上打分。407 个已打标事件上（多数是接入时的回填预测），新 − 旧的所有 Δ 都不显著。线上弃权率 50%，远高于离线的 10–21%，弃权阈值不能直接迁移。
10. **结论**：第二阶段把能力补齐了（自监督目标、校准 / 弃权、冷启动和在线自适应、场景通用输入、全双工控制骨架、ONNX、影子并行），但**没有在任何关键头上带来稳定、显著的提升**。真实数据仍然太少（被叫头 test 只有 8–12 个正例）。**仍然不能接管任何真实决策**，继续影子模式积累数据。

### 1.1 统一事件流与输入（`tidal/features_g.py`）

- 每个事件：10 维时间 / 节奏 / 相对角色特征（和第一阶段 T 口径相同，严格因果）+ 可选的参与人数块（log(1+人数) + 已知位）+ 可选的模态块（已知位 + 文本 / 语音 / 视觉 / 其他）。
- **没有场景枚举**。参与人数是连续特征；训练时两个可选块各以 0.5 的概率整体丢弃，"未知"和"被丢弃"在输入上完全一样（零向量 + 已知位为 0）。
- 发言人身份、文本可得性仍然**不作为输入**（第一阶段 §5 的可得性泄漏）。

## 2. VAP 式未来事件投影（`tidal/vap_targets.py`、`tidal/vap.py`）

- **目标**：对每个事件，预测未来 5 个时间桶（0–2、2–5、5–15、15–60、60–180 s）里，4 个**相对**通道是否有人发消息：self（机器人 / 主播）、human（任何非 self）、current（这条消息的作者再发，需要发言人身份，未知时屏蔽）、others（作者以外的人，未知时屏蔽）。超出观测末端的桶屏蔽。共 20 个二分类输出。只需要时间戳和相对角色，所以在任何场景（群聊、1:1、直播、通话）都一样定义。
- **训练**：第一阶段（预训练）只训练投影目标，用上所有事件；第二阶段（微调）从预训练权重初始化，训练 6 个下游头，投影作为辅助损失（权重 0.5）。"被叫"和"说/等/不说"两个头的合成样本权重为 0（第一阶段发现合成数据对它们有害）。
- **配置**（各 3 个种子，单线程 CPU）：P2a = 真实 + LLM 合成，先预训练（约 3.5 分钟 / 次）；P2b = 再加脚本直播和 1:1（约 9 分钟 / 次）；P2n = 不预训练（消融）。**选型规则事先定好**：真实 val 下游损失均值最低的配置（P2a 3.967 < P2n 3.990 < P2b 4.003），再取其中 val 最好的种子 → `P2a_s1`。加入脚本合成流（P2b）让真实 val 变差。

## 3b. 身份无关的角色、冷启动与在线自适应（`tidal/coldstart.py`）

- **身份无关**：输入只有相对角色（self / other；投影目标里还有"当前作者"），没有用户 ID、没有用户嵌入，新会话不需要注册任何人。
- **冷启动协议**：在 2 个**未见群**里，每 120 个事件设一个"加入点"，模型从零历史开始（特征由流式特征器从加入点重新计算，上下文不跨过加入点），只在加入后的前 N = 20 / 50 / 100 个事件上打分。共 18 个加入段，分块 bootstrap 以加入段为块。参与人数是会话级信息，加入时已知。
- **系统**：warm = 同一模型、同一批事件、完整历史（参照上限）；cold = 只看加入后的事件；cold+adapt = cold + 按会话在线重新校准（二分类 sigmoid(a·z+b)，多分类 softmax(z+b)），**只用预测时刻已经揭晓的标签更新**（每个头的揭晓时延：EOT 20 s，续话 200 s，被叫 / 动作 / 接话 60 s，重检 300 s），学习率按头在真实 val 上选（EOT 和接话选到了 0，即不自适应）；base_online = 会话内已揭晓标签的运行基率（向 train 先验收缩）；lr_G = 同样冷启动特征上的 LR。

| 头（指标） | N | n(正例) | warm | cold | cold+adapt | base_online | lr_G | cold − warm | adapt − cold | adapt − lr_G |

## 4. 场景通用与留一场景（`tidal/loso.py`）

- **做法**：同一个模型（同样的输入、同样的 6 个头 + 投影），只改变训练数据的来源，在训练时完全没见过的场景上测试。对照组是**同一训练数据上的 LR**（lr_G，同特征），所以"模型 − LR"比较的是两种学习器的迁移能力，不是数据量。指标：二分类 PR-AUC，多分类 macro-F1；按"会话 × 5 分钟"分块（合成）或"会话 × 小时"分块（真实）bootstrap。
- **注意**：直播和 1:1 都是脚本合成的；直播流里"说完一轮"和"人类接话"的正例率接近 1（0.92 / 0.999），这两个头在直播上 PR-AUC 没有信息量。真实测试集（test_time + test_group）恰好全部是群聊，所以"→ 真实群聊"和"→ 真实"是同一批行。
- **"回应哪条事件"**：在合成直播里，主播每次开口时，候选是此前 60 s 内的所有观众事件（平均 60 个），指针 = p_speak × 时间衰减，指标是 hit@1。
- **主要发现**：
  1. **没见过直播 → 直播**（A1/A2）：EOT / 续话 / 接话的 PR-AUC 只等于正例率（ROC-AUC ≈ 0.5），说 / 等 / 不说和重检几乎完全失败（A1 说/等/不说 macro-F1 0.006–0.012，同数据的 LR 0.321）。投影平均 AUC 0.57–0.59，LR 0.69。"回应哪条弹幕" hit@1 0.06–0.08，**低于"回应最新一条"（0.105）**，高于随机（0.028）。即使训练里有直播（in-domain 参考），hit@1 也只有 0.09–0.105，和"回应最新一条"持平。
  2. **没见过 1:1 → 1:1**（A3/A4）：EOT 比同数据 LR 显著更差（−0.069 / −0.024），续话持平或更差；说/等/不说在 A3 更好、A4 更差，不稳定。
  3. **完全不用真实数据 → 真实聊天**（B）：EOT、续话、被叫都显著差于同数据 LR，被叫 = 先验（合成数据不给被叫头监督）；说/等/不说、重检略好于 LR，但都远低于用真实数据训练的模型（0.32 vs 0.41，0.14 vs 0.18）。
  4. **完全没有群聊数据（只用合成直播 + 1:1）→ 真实群聊**（C）：EOT 0.808 ≈ 先验 0.804，续话 0.544 低于先验 0.596，被叫无信号；说/等/不说、重检略高于先验，但只有 0.03 / 0.05（用真实群聊训练的模型是 0.40 / 0.18）。**群聊的话轮规律不能从直播或 1:1 学到。**
  5. **in-domain 参考**：只要训练里有目标场景，模型和同数据 LR 相比持平或略好（真实群聊：EOT +0.023~+0.033，说/等/不说 +0.08，重检 ±0.02；被叫在只用真实 + LLM 合成时 +0.219 [+0.098, +0.396]，但 test 上只有 20 个正例，加了直播 / 1:1 数据后这个优势消失，seed 间波动很大：0.10–0.28）。注意这里的 LR 只是同数据上的对照，不是 §2.2 里 val 选出的最强基线；对最强基线的比较以 §2.2 为准。
- **结论**：输入层面已经场景通用（没有枚举，人数是连续特征，未知可置零，人数未知时性能不变：EOT 0.855 vs 0.856），但**能力层面不跨场景迁移**，每个场景都需要自己的数据。合成流的参数是手写的，这些结论只能说明脚本合成流之间、以及合成流和真实群聊之间差别很大。

## 5. 全双工 tick 控制骨架（`tidal/duplex.py`、`tidal/duplex_sim.py`）

- **结构**：每 100 ms 一个 tick。输入有 4 路：本 tick 到达的事件（经流式 VAP 编码器 `EventEncoder` 逐条更新，复用 `P2a_s1` 的 GRU）、音频帧特征、视觉帧特征、**她自己的输出状态**（是否正在说、已说时长、是否被打断）。`TickModel`（GRU，74,951 参数）输出控制动作：沉默 / 开始 / 继续说 / 让出 / 被打断后接着说 / 附和 / 冷场时主动开口，外加"回应哪条事件"的指针（p_speak × 时间衰减）。**控制和内容分离**：模型只决定"什么时候说、回应谁、说多长"，内容由外部 LLM 生成；控制器不看文本内容。
- **音频、视觉前端只是接口**：sanity 测试里用的是模拟出来的 VAD 概率（带噪声）和占位视觉特征，不是真的音频或视频。
- **合成 sanity 测试**（60 个合成会话，±300 ms 容差；标签来自脚本里的规则参考策略，所以这只检验"能否学会并实时执行一个控制策略"，不说明真实效果）。规则控制器的 3 个参数（VAD 去抖 tick 数、安静阈值、冷场等待秒数）在 40 个 val 会话上网格调参：

| 动作 | 模型 F1 | 规则控制器 F1（val 调参） |
|---|---|---|
| 开始说 | **0.998** | 0.902 |
| 让出（被打断 / 对方开口） | 0.807 | **0.882** |
| 被打断后继续 | **0.905** | 0.476 |
| 附和（backchannel） | **0.771** | 0（规则没有这个动作） |
| 冷场时主动开口 | 0.817 | **0.972** |

  "让出"的延迟相对参考策略平均 −0.07 tick。只看 VAD 的"让出"规则：1 tick 去抖 F1 0.24，3 tick 去抖 0.887。**结论**：模型在"让出"和"冷场开口"上不如一个调过参的简单规则，这两项上线时应先用规则。

- **CPU 实时基准**（单线程，PyTorch eager，Intel Xeon，编码器 + tick 模型共 573,993 参数，每个配置 2,000 tick）：

| 每 tick 到达事件数 | p50 | p95 | p99 | 10 Hz 下 RTF（p95） | 满载可持续 Hz | 按 p99 的保守 Hz |
|---|---|---|---|---|---|---|
| 0（空闲） | 0.13 ms | 0.20 ms | 0.30 ms | 0.002 | 6,795 | 3,380 |
| 1（每秒 10 条） | 0.64 ms | 0.82 ms | 1.01 ms | 0.008 | 1,499 | 988 |
| 5（每秒 50 条） | 3.36 ms | 4.52 ms | 5.34 ms | 0.045 | 301 | 187 |
| 20（每秒 200 条，直播高峰） | 24.5 ms | 38.7 ms | 41.9 ms | 0.387 | 41 | 24 |

  **5–10 Hz 的要求在所有负载下都满足**（最坏情况 10 Hz 时 p99 也只占 tick 预算的 42%）。成本主要来自逐条事件的编码器更新；每 tick 20 条以上时可以把同一 tick 的事件批量编码。测量时机器上还有别的 nice 19 训练任务在跑，数字偏保守。

## 6. ONNX 导出（`tidal/export2.py`）

- `P2a_s1` 导出为 ONNX（opset 17），2.0 MB（fp32）。在 1,000 个真实窗口上和 PyTorch 对比：所有头的最大绝对差 ≤ 2.7e-7，决策 100% 一致。
- 左侧补零的不变性：同一段历史分别补到 64 和更短长度时，输出最大差 0.035（GRU 会在补零位上更新状态）。影子推理和导出都固定补到 64，所以线上和离线一致；但流式 `step()` 和定长窗口不是逐位相等，这是已知限制。

## 7. 影子模式：新旧模型并行（`tidal/shadow/`）

- 新模型以第二个系统接入原有的定时任务（每 10 分钟，第 3、13、23… 分钟；flock 防重入、nice、超时）。新旧两个系统在**同一批事件、同一批延迟标签**上打分，预测和标签都只写一次；对生产库只读。新系统额外记录弃权（"等一下再看"）。
- 冻结配置：温度、阈值和弃权阈值都在 val 上确定，之后不再改动。
- 结果（2026-10-07 15:04 至 10-08 11:08 UTC+8，407 个已打标事件；会话 × 小时分块 bootstrap）。第二阶段系统 10-08 10:33 才接入，这些事件上的预测大多是接入时的**回填**：只用消息到达时已有的信息（T 口径严格因果），但不是实时做出的。之后的事件两个系统都是实时打分。

| 头 | 新（P2） | 旧（第一阶段） | 新 − 旧（95% CI） |
|---|---|---|---|
| EOT（PR-AUC） | 0.911 | 0.897 | +0.012 [−0.013, +0.026] |
| 自我续话（PR-AUC） | 0.906 | 0.886 | +0.026 [−0.020, +0.081] |
| 被叫（PR-AUC，9 个正例） | 0.245 | 0.184 | +0.039 [−0.049, +0.144] |
| 人类接话（PR-AUC） | 0.805 | 0.766 | +0.020 [−0.042, +0.089] |
| 说 / 等 / 不说（macro-F1） | 0.418 | 0.419 | −0.005 [−0.038, +0.018] |
| 重检延迟（macro-F1） | 0.181 | 0.162 | +0.009 [−0.025, +0.041] |

  **所有差值都不显著。** 线上弃权率 50%（离线 10–21%），作答部分准确率 0.812，弃权部分 0.783，差别很小：val 上定的弃权阈值迁移不到线上，需要用影子数据重新定（要单独留出一段时间做评测）。
- 定时任务在接入新系统后一直正常运行（截至 11:08 共 50 次成功、0 次失败；11:08 手动运行一次也正常）。两个系统的预测数一致（各 417 个事件），最新事件也一致。

## 8. 局限和下一步

- **真实数据仍然太少**：7 个会话，被叫头 test 只有 8–12 个正例，影子数据 394 条。大多数 CI 宽到无法区分 ±0.05 的差异。影子模式需要再积累几周。
- **直播和 1:1 是脚本合成的**，参数是手写的猜测；留一场景的结论只能说明"脚本流之间不迁移"，不能推到真实直播。需要真实（或至少公开的）直播 / 1:1 时间戳数据。
- 全双工部分只有控制骨架：音频 / 视觉前端是占位，sanity 测试的标签来自规则参考策略。下一步是接一个真实 VAD（如 Silero，CPU 可跑）并在公开的双人对话语料上评测。
- VAP 目标没有超过 LR：可能是 20 个输出太粗、真实数据太少，也可能这些时间特征本来就接近线性可分。可以试更细的时间桶、对比式目标，或在更大的公开对话时间戳数据上预训练。
- 在线自适应对被叫头有害，应在该头上关闭；弃权阈值要用线上数据重新定。
- ONNX 的补零不变性、温度缩放在正例率漂移下变差（自我续话），都需要在下一阶段处理（例如用 mask 的 GRU、按会话的温度）。
- 没做的：seed 集成 / MC dropout / 保形预测、量化、蒸馏、剪枝。

## 9. 复现

```bash
python -m tidal.dataset2                  # 构建统一事件流（含脚本合成的直播 / 1:1 流，不调用任何 API）
bash scripts/p2_train_all.sh              # VAP 预训练 → 微调（3 种配置 × 3 seed + 留一场景模型），CPU 单线程
python -m tidal.evaluate2                 # 下游、校准（ECE）、风险-覆盖、弃权
python -m tidal.report2                   # 投影质量、人数未知时的稳健性
python -m tidal.coldstart                 # 冷启动 + 在线自适应
python -m tidal.loso                      # 留一场景
python -m tidal.duplex_sim train P2a_s1 && python -m tidal.duplex_sim eval && python -m tidal.duplex_sim bench P2a_s1
python -m tidal.export2 P2a_s1            # ONNX + 一致性
python -m tidal.shadow.setup2 P2a_s1      # 冻结影子配置；之后由定时任务自动并行打分
pytest -q
```

真实数据通过私有适配器接入（公开仓库里没有）；没有真实数据时，可以只用合成流跑通整条管线。
