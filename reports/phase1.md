# tidal 第一阶段报告（文本 + 时间节奏）

> 日期：2026-10-07（UTC+8）｜全程只用 CPU（8 核 Xeon，训练和评测时 torch 最多用 4 个线程）
> **公开版说明**：这是脱敏后的副本。删去了数据源的内部表名和部署细节、会话标识、机器人名字，以及与私有部署相关的运维备注；不含任何真实消息样例。真实数据、在真实数据上训练的权重、逐事件的评测输出都不公开。
> 原则：评测只用真实留出数据；合成数据只用于训练；真实聊天数据不进 git、不上传、不发给 DeepSeek。

## 0. 结论速览

1. **上游没有完整的消息日志。** 每条消息的时间戳都有，但文本和发言人只能从机器人的 LLM 上下文快照里拼回来，覆盖了 29% 的消息（10,973 条里有 3,172 条）。这是本阶段最大的限制。
2. **发现并处理了一个严重的选择性泄漏。** 某条消息有没有文本，取决于机器人后来有没有走 LLM 回合，所以"有没有文本"本身就能预测"机器人说话"（只看可得性模式的探针 ROC-AUC 为 0.93）。为此评测分成两种口径：
   - **T**：只用时间和角色特征，覆盖全部消息，不存在这种泄漏；
   - **TS**：时间 + 发言人 + 文本 + bge 嵌入，序列只由有文本的消息组成。
3. **模型在任何一个头上都没有稳定、显著地超过最强基线。** 多数头的 Δ 为正（+0.01 到 +0.05），但 95% CI 跨过 0。T 口径下只有三处显著为正：自我续话（时间切分）、动作（时间切分）、被叫（相对 val 选出的基线；但相对 test 上事后最好的基线并不显著）。另有一处显著为负：T 口径动作头在未见群上（−0.097）。**真实数据太少（TS 训练位置约 2.2k），这个结论不能外推。**
4. **合成数据**：对 EOT、续话、重检延迟、人类接话这几个头有小幅正面作用（3 个种子的均值多数 +0.01 到 +0.04）；对"被叫"和"说/等/不说"这两个头**有害**（−0.03 到 −0.14）。
5. **选定模型**：`TS_rs_gru_s1`（GRU，55 万参数，真实 + 合成数据训练）。导出为 `models/TS_rs_gru_s1.onnx`（2.2 MB），ONNX 和 PyTorch 输出的最大差为 2.4e-7。单线程下每次决策（bge 编码 + 主干）p50 2.25 ms、p95 2.78 ms，进程 RSS 约 110 MB。
   降级备选：`T_rs_gru_s1`（只用时间特征，1.95 MB，p50 0.99 ms，RSS 69 MB）。
6. **结论：不能直接上线。** 下一步是影子模式：在线记录完整的事件流，补齐数据，并和旧策略、规则基线做对比。

## 1. 数据

### 1.1 来源（机器人的事件库，只读）

数据库会话强制只读（`default_transaction_read_only=on`），并核验过：在该会话里建表会被拒绝。没有任何写入，也没有改动上游的任何东西。原始导出只留在本地（chmod 700），不进 git。

| 数据 | 用途 | 局限 |
|---|---|---|
| 消息映射表 | 每条消息的会话、方向（入站 / 出站）和时间戳，共 10,973 条 | 没有文本，没有发言人 |
| 决策回放（入站消息事件，9,392 条） | 机器人实际的决策（speak / silent / act），以及注意力原因（是否被 @ 或被回复） | 没有会话 ID；预决策特征是最近才开始写入的 |
| LLM 上下文快照（774 条） | 最近约 16–19 条消息（发言人和文本，有顺序，没有时间戳），以及当前消息的 @ 和回复标记 | 只在机器人走 LLM 回合时才会产生 |

**对齐方法**（私有适配器，未公开）：
1. replay 和 mapping 按时间戳一对一贪心匹配。observe_only 类事件比 mapping 晚 0.03–0.2 s；attend / must_handle 类因为合并等待，晚 0.2–13 s。匹配率 94%（8,826 / 9,392），其中有歧义的占 2.3%。
2. 用回合 ID 找到 replay，作为锚点定位当前消息。
3. 从锚点向前，把最近消息窗口和 mapping 序列按方向对齐（精确匹配，失败时退回到带跳过的 DP）。
4. 同一条消息常被多个快照覆盖，按多数票取文本和发言人。在有多票的 1,988 条消息上，投票一致率为 91%，也就是**对齐噪声约 9%**。

### 1.2 隐私

- 用户 ID、会话 ID、消息 ID 一律做带盐 HMAC 哈希，盐只保存在 `.secrets/`。
- 文本先脱敏再落盘：手机号、5–12 位数字（QQ 号等）、URL、邮箱、身份证号、CQ 码、抖音分享口令都替换成占位符。
- `data/`、`.secrets/`、`logs/` 和模型权重都写进了 .gitignore。git 里只有代码、配置和指标 JSON。

### 1.4 标签启发式及其噪声（`tidal/labels.py`）

- **EOT**：发言人已知时才打标。下一条消息间隔 ≥ 20 s（与上游机器人的连发合并窗口一致）→ 1；否则看下一条的发言人，是别人 → 1，是本人 → 0；下一条发言人未知 → 屏蔽。
  噪声：对齐错误约 9%；20 s 阈值是人为设定；被屏蔽的样本偏向片段边界。
- **自我续话**：只在 EOT=1 的消息上定义。同一发言人在 180 s 内再次发言 → 1；窗口内全是已知的其他人 → 0；窗口内有未知发言人 → 屏蔽。
  对机器人自己的消息总能判定（未知发言人不可能是机器人）。
- **被叫（addr）**：只看群内入站消息。replay 的注意力原因为"被点名"或"回复机器人"，或快照里当前消息带 @ / 回复标记，或文本里出现机器人的名字 → 1。私聊一律视为被叫，不参与评测。
  噪声：没有 replay 的消息只能靠名字判断。
- **说 / 等 / 不说（act）**：该消息对应的 replay 选择了 speak → 说；否则如果 60 s 内同一会话里后续某条消息的决策是 speak → 等；其余为不说。act 记作不说（共 73 条）。
  这是在模仿旧策略（off-policy），带着旧策略的偏差。
- **人类接话（hreply，辅助信号，回答"群里的人此刻会不会接话"）**：60 s 内有另一个人类发言 → 1；有未知发言人 → 屏蔽。
- **重检延迟（recheck）**：到会话下一条事件的时间，分桶为 [<2, 2–5, 5–10, 10–20, 20–60, 60–300, ≥300 s]。
- **合成数据**：用同一套启发式从生成的消息流推导标签。被叫额外采用生成器的 addr_bot 标注；"说"定义为下一条消息是机器人发的。
  一致性检查：生成器标为 eot 的消息中，有 93% 被启发式判为 EOT=1；标为 unfinished 的消息只有 29% 被判为 EOT=1；被标为 self_cont 的消息之前那个回合结束点，启发式判为续话的比例是 97%。

## 2. 合成数据（DeepSeek）

- 提示词只包含手写的抽象描述：话题列表、风格列表、机器人的行为方式、人数和条数。**没有任何真实消息。** 使用 JSON 输出，关闭思考模式。
- **调用**：共 1,502 次，成功 1,098 次，失败 404 次（大多是 HTTP 429 限流）。
- **Token**：输入 611,042，输出 2,217,310。
- **费用**：按偏保守的价格（输入 ¥3/M、输出 ¥9/M）估算为 **¥21.79**；按官网当前高峰价（¥2/M、¥8/M；所有调用都在工作日 15:16–15:35 的高峰时段）约 **¥18.96**。两个口径都在 ¥30 / 3,000 次的上限以内。
- **校验和去重**：每段至少 20 条消息；字段合法；dt 在 0–7200 s；至少 2 个真人且有机器人；机器人消息不超过 60%；去掉完全重复的会话，以及消息集合 Jaccard ≥ 0.3 的近重复会话。最终保留 1,015 段会话、61,676 条消息。
- 合成文本和真实文本（规范化后长度 ≥ 6）完全重合的只有 1 条，是泛用短语。评测切分中合成样本为 0 条。

## 3. 嵌入（bge-small-zh-v1.5，int8 ONNX，CLS 池化 + L2 归一化）

- 按 sha1(文本) 缓存，共 55,382 条，`data/emb/`。
- 吞吐（batch 64）：1 线程约 1,264 条/秒，4 线程约 2,900–3,700 条/秒。单条延迟 1 线程 p50 0.95 ms / p95 1.11 ms。
- int8 和 fp32 输出的余弦相似度：均值 0.990，最低 0.960；最近邻一致率 0.87。

## 4. 基线与模型

- **基线**（`tidal/baselines.py`）：只用真实 train 训练，超参数和阈值在真实 val 上选。
  1. 多数类；
  2. 间隔阈值：单个时间特征上的一维逻辑回归，特征在 val 上挑选；
  3. LR + 手工特征：间隔、长度、标点、疑问语气词、未完标记、@、名字、连发计数、时段等；
  4. GBDT + 手工特征；
  5. 单句文本：只对当前这一条消息的 bge 嵌入做 LR（只在 TS 口径下有）。
- **模型**（`tidal/model.py`）：
  - 输入是最近 64 个事件，每个事件 = 特征投影 +（TS 口径下）文本投影；
  - 主干是 2 层 GRU（隐藏层 192），或 2 层因果 Transformer（d=128）；参数量 48–55 万，低于 200 万的上限；
  - 6 个头联合训练，带屏蔽的 BCE / CE；AdamW，按 val 损失早停；
  - 训练后在 val 上对每个头单独做温度缩放。
- **训练配置**：
  - 真实 vs 真实 + 合成（合成样本的权重 λ 为 0.5，另扫了 0.2 和 1.0）；
  - GRU 主配置各跑 3 个种子，Transformer 跑 1 个种子；共 20 次训练，每次约 1–5 分钟。
- **选型规则（事先定好）**：取 val 总损失最低的检查点。TS 口径是 `TS_rs_gru_s1`（4.503），T 口径是 `T_rs_gru_s1`（3.911）。

## 5. 泄漏审计（`reports/leakage_audit.json`）

- **特征因果性**：随机抽 300 个事件，把它们之后的消息截掉再重算特征，不一致数为 0。把所有标签来源列（addr_src、bot_act_src、y_*）打乱后，特征完全不变。`features.compute` 不读取 attention、chosen_action、delivered、cur_addressed / cur_reply、tags 等任何标签来源字段。
- **模型因果性**：随机改动第 40 位之后的输入，前 40 位的输出差为 0.0（两个选定模型都是）。
- **单特征扫描**：在 train 上，没有任何单个特征的 AUC 超过 0.85。
- **切分**：未见群在 train 中出现 0 次；train 和 val 的最大时间都早于下一个边界减去 embargo；评测集中合成样本为 0 条。test 中有 42 条文本也在 train 中出现过，全部短于 8 个字（"哈哈哈"一类）。
- **可得性泄漏**（关键）：在全部事件上，"附近有没有文本"这一模式预测"说"的 ROC-AUC 为 0.93，预测"被叫"为 0.88。因此：
  - has_text、speaker_known 等可得性标志**永远不作为输入**；
  - T 口径完全不看文本和发言人；
  - TS 口径的序列只由有文本的消息组成。
  TS 子集内部仍有一点残余信号（历史可得性模式对"说"的 ROC 为 0.60，对"被叫"0.64，对续话 0.62），而且 TS 子集本身偏向机器人活跃的时段。所以 **TS 口径的绝对数值偏乐观；模型和基线的相对比较受影响较小，因为它们在同一个子集上评测。**
- 平台的 @ 和回复标记**不作为模型输入**：它们是"被叫"标签的来源。上线时由决策层的硬规则处理（被 @ 必须回应）。

## 7. 问题与不足

1. **数据**：没有消息日志。只有 29% 的消息有文本和发言人，对齐噪声约 9%，覆盖集中在机器人活跃的时段。真实数据只有 19 天、5 个群，而且分布很不均衡。
2. **正例太少**：test 里"被叫"只有 7–12 个正例，"说"只有 29–34 个，CI 很宽，无法下结论。
3. **动作标签有问题**：它是在模仿旧策略，旧策略本身在漂移（说话率 9.8% → 2.7%），而且有离策略偏差。
4. **合成数据有分布差**：伤害了"被叫"和"动作"两个头。生成器的 dt 节奏和真实群的差异也没有校准。
5. **TS 口径的残余可得性偏差**：见第 5 节。
6. **线上依赖**：选定模型依赖 bge 编码。如果线上拿不到文本，必须降级到 T 模型。

## 8. 建议的第二阶段

1. **先做影子模式和数据（最高优先级，在任何上线之前）**：
   - 在使用方（机器人）里增加一个**只读的事件记录**：每条入站和出站消息的时间、脱敏后的文本或只存嵌入、哈希后的发言人、@ / 回复标记、机器人的决策和 propensity。完整事件流可以消除可得性偏差和对齐噪声。
   - tidal sidecar 用影子方式并行运行，只记录不执行，和旧策略、本报告里的 GBDT 规则基线对比"误打断率"、"@ 回应率"和"发言率"。
   - 积累 4 周以上的数据后，重做时间切分和群切分的评测。在 CI 显著优于基线之前，**不接管任何真实决策**。
2. **改进标签和训练**：
   - EOT 改成离散时间风险分布（H1 的设计）；
   - 加入 VAP 式的自监督"未来活动"头，在全部 1 万多条只有时间的事件上做预训练；
   - 动作头加 IPS 加权（用 replay 的 propensity）；
   - 合成数据按真实统计（发言率、叫法、dt 分布）重新配比，或者只用于节奏类的头。
3. **图片和视频**：用 Chinese-CLIP RN50（视觉塔 int8）生成嵌入，加零样本中文标签（表情包 / 截图 / 猫……），视频均匀抽 4–8 帧做池化；QQ 表情 ID 加一个可学习的嵌入。
4. **语音**：SenseVoice-Small（int8，sherpa-onnx；输出转写、情绪、声学事件），加 Smart Turn v3.2 的声学 EOT 概率作为事件特征。SenseVoice 按需懒加载。
5. **工程**：
   - 推理放进 Rust `tidal-core`（ort），把特征计算和标准化参数一起移植过去，并用本仓库导出的 ONNX 做逐位一致性测试；
   - 决策层里保留硬规则：被 @ 必须回应、发言率预算、深夜静默。
